# Module Map

The v3 core sequence is mandatory for substantial new, rebuild, or replacement work:

1. Shape
2. Product principles and calibration
3. Concept proof
4. Foundation plus signature
5. Problem / solution / implementation review

References support the sequence. They do not replace it.

## Core owners

| Stage / need | Primary owner | Optional support |
| --- | --- | --- |
| Shape user need, outcome, irreducible core, non-goals | `shaping.md` | `real-content-first.md`, `task-continuity.md` |
| Create product-specific decision principles | `product-principles.md` | `origin-principles.md` |
| Calibrate against platform and best-in-class quality | `reference-calibration.md` | `visual-direction.md`, `craft-floor.md` |
| Prove the vertical slice before full build | `concept-proof.md` | `structural-direction.md`, `experience-dynamics.md`, `art-direction-media.md` |
| Separate problem, solution, and implementation critique | `review-stages.md` | `review-protocol.md` |
| Positive readiness and “nothing obviously wrong” bar | `quality-bar.md` | `craft-floor.md`, `coherence-floor.md`, `taste-gate.md` |

## Ownership boundaries

- `shaping.md` decides what should be built. `structural-direction.md` decides how an approved problem may be spatially expressed.
- `product-principles.md` creates local decision rules. `origin-principles.md` preserves historical project context.
- `concept-proof.md` decides whether a solution deserves full implementation. It is not a browser QA substitute.
- `reference-calibration.md` sets external quality bars without copying references.
- `review-stages.md` separates critique by maturity. `review-protocol.md` separates reviewer evidence from generator self-justification.
- `quality-bar.md` owns positive readiness and quality vetoes. `evidence-gate.md` owns objective failures and blocked evidence.
- `experience-dynamics.md` chooses interaction logic. `motion-interaction.md` implements motion after the logic is accepted.
- `task-continuity.md` owns state lifetime and return. `interaction-contracts.md` owns one consequential interaction.
- `craft-floor.md` owns implementation details, not concept rescue.
- Historical evidence, benchmark results, and release reports are never automatic runtime instructions.
